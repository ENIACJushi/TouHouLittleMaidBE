## 总结论

1. **方向通过**：可达场 + 区块级共享扫描 + 女仆只查缓存；能打到多女仆重复扫、空田按人节流、落脚点只建不补。
2. **不宜按正文直接开工 P8a**；更不宜在契约补齐前让 P8b 退场 `collectTasks`。
3. **已拍板 1～5 维持**：活动圈刷新、方案 A（diff）、瓜不查朝向、不订阅方块事件、构建不测 `closest`（但查询就绪批上限要测）。
4. 三份一致：**先补契约 → 按分期落地**；无 100% 证据处只列方向，不指定唯一做法。

按当前正文开工会打偏的两处（Claude 强调）：

- **性能模型找错热点**：稳态最大消费者是出发找路的 `rereadLeaf`，不是建层；P8a 只换建层读口，基准好看、游戏里总读量几乎不变。
- **刷新「邻居」覆盖不了跨沟**：可逆步含 `SprintGap`（`GAP_MAX=4`），四邻局部刷新会留下与地形不符的跨沟边。

## 与现状对齐（方案必须接住的事实）

| 现状 | 对 P8 的含义 |
| --- | --- |
| `StandNode` 存**支撑格**；`Farm.goalStandOfTask` 是作物格 `y-1` | `InterestPoint.standKeys` 必须是支撑格，不能是脚位或动手格 |
| `scanChunk` 按格 `createLeaf`，合并结果依赖访问顺序 | P8a 验收不能要求「场编号数字相同」，只能要求**连通分量**相同 |
| `rereadLeaf` / `reversibleSteps` / `expandEdges` 都走 `StandableCache.getFlags` | 扫描快照必须能替换这套读口，不能再并存「按 typeId 猜 flags」 |
| `StandableCache.getFlags` 未加载 → `MISSING`（`passable=false`，不当空气） | `getBlocks` 没返回的格**不能**直接当空气 |
| `evalBlockFlags` 对未知方块看 `isSolid`：非 solid 默认可过 | 「nonAir 且不在薄片组 → 不可过」会改变未知方块语义 |
| `layerReady`：`pendingY.length > 0` 则**整块**未就绪 | 圈内首建 / 刷新若把多层推进 `pendingY`，已建层也会变 `unready` |
| `ensureStandHeight` 只请求一点的 `y-1,y,y+1` | 它不是「把活动圈铺满」的扫描单元 |
| 活动圈只有 XZ，没有 Y | 「范围内已建层」可能远多于 3 层 |
| Farm 已有 `getBlocks(土地 ∪ 成熟 permutation, allowUnloadedChunks=true)` + P7 队列 | P8 不是第一次引入 getBlocks；`collectTasks` 退场前必须先有圈内首建 |
| `FarmBlocks` 按模组 tester 动态装作物 / 土地 / permutation；`landHasSeed` 按土地配种子 | Farm 兴趣名单权威是 `FarmBlocks`，不是「背包有没有任意种子」 |
| 甘蔗 `collectTasks` 以脚位为中心上下追 `MAX=3`，并改写搜索 y | 兴趣点若只挂女仆脚下 3 层，斜坡 / 高差会漏 |
| 可可扫描高度脚位 `+4`～`-1`；建层只保支撑 `y-1..y+1` | 兴趣体积跟落脚点层绑死会漏高处可可 |
| `CropRoute` 的 `cellClaims` 与 Farm 不互通，且**没有**认领 N 队列 | 任务板不能共用一张占用表；P8d 前不能假装队列已对齐 |
| 调度入口三处（pulse / 9s search / follow 完成） | `SpeedController` 退场后应收成一次索要 |
| `rereadLeaf` 每个叶子 `new StandableCache`；`findReversiblePath` 每拍最多展开 256 叶且逐个 reread | 出发找路方块读取与路径长度成正比，无跨叶子复用 |
| `scanChunk` 每拍 `new StandableCache`；一层 256 格，每拍最多新建 64 叶 | 密集田一层跨多拍，边界邻居每拍重读 |
| `REVERSIBLE_REACH = GAP_MAX` 已导出并注明用途，全仓库无人引用 | 刷新半径应复用它，不要另写「四邻」 |
| `classifyFieldClaim` 的 `different`：`!left\|\|!right`（无叶）与两边 `fieldId` 不同都返回 `different` | 闸门按 `different` 刷新会分不清「表可能缺点」和「静态分场」 |
| `BlockFilter` 多个 include 之间是**或** | 可可四个朝向一次查询即可 |
| `getBlocks(..., allowUnloadedChunks=true)` 文档：只检查体积内**已加载**区块 | 「没返回 = 空气」在区块边缘必错（已声明行为，非待测猜测） |
| `getBlocks` 可抛越界 / 未加载等 | 扫描体积先过现有 `clampBoundsToDimension` |
| `Cocoa.acquireAt` 无论如何都 `getBlock` 核对 `age` | 正文「补种无需 getBlock」不成立 |
| `standsBeside` 只取 `task.y` 与 `task.y-1`，从不把 `task.y+1`（站在瓜上）当候选 | 「瓜顶算落脚点」是**新增行为**，不是放宽 |
| P7c「按列更整齐」来自 `collectTasks` 螺旋列序 + `maxCount=25` 截断，再 `assignNext` 按距离取 | 整齐的是**候选窗口**，不是排序键 |
| 占用释放入口三处 fan-out：`leaveWork` / `onMaidInvalid` / `settleReturned` → 四个工作的 `abandon` / `markStale` / `settle` | 占用迁任务板时这些入口必须一起迁 |
| `FarmBlocks.getLands()` 按「种子 × 土地」重复 push；含 `soul_sand` | 喂 `includeTypes` 前去重；「耕地」应为「土地名单」 |
| `@minecraft/vanilla-data` 是 devDependency；`src` 未引用；构建 `tsc` 直出无打包器 | 完整 typeId 可**构建期**由谓词生成；运行时不能 import vanilla-data |
| Bedrock 只有 `minecraft:air`；另有 `light_block_*`、`structure_void` 等非空气非 solid | `excludeTypes: ["minecraft:air"]` 足够；后者是「nonAir 且不在薄片 → 墙」的反例 |

## BLOCKER（必须先补契约）

### B1. 「没出现在 nonAir」当作空气 —— 建层正确性

**原则：LSP**（与现 `StandableCache` 契约不一致）

**问题：** 正文扫描步骤 1：不在 `nonAir` 里的格即空气、当净空。现实现：未加载 / `getBlock` 失败记 `MISSING`，**不当**可过、不当可支撑。`getBlocks(..., allowUnloadedChunks=true)` 文档已写明只检查已加载部分。按字面算法会：把未加载格建成假落脚点，或 diff 时把真落脚点当成「消失」删掉。风险节写「需实测」，算法却已把「缺省 = 空气」写成默认。P8a「同一块地落脚点集合相同」在区块边缘会系统性失败。

**建议：**

1. 扫描结果分三态：空气 / 非空气 / **未知**（未加载或 API 未覆盖）。
2. 未知格：不 `createLeaf`、不 `removeLeaf`、不写兴趣点（与今天 `MISSING` 一样跳过）。
3. `allowUnloadedChunks` 实测放到 **P8a 开工前**；未测之前刷新范围只能扫已加载区块。Farm 现有调用只能证明「API 能跑」，不能证明「没返回 = 空气」。

---

### B2. 「名单缺项只影响性能」与步骤 3 字面算法矛盾

**原则：LSP**（谓词结果必须与 `evalBlockFlags` 可互换）

**问题：** 风险节说子串盖不住的模组方块在第 3 步逐格 `getBlock`，缺名单只慢不快错；步骤 3 却写「脚/头在 `nonAir` 且不在薄片组 → 不可穿过，无需读」。未知非空气若跳过 `getBlock`，会把「引擎 `isSolid=false`、今天默认可过」的方块判成墙（`light_block_*`、`structure_void` 是现成反例）。`evalBlockFlags` 依赖 `Block.isSolid` / `isLiquid` / `isAir`，不是 typeId 纯函数；按 typeId 缓存 flags 只对已证明与状态无关的类型合法。

**建议：flags 权威仍是 `evalBlockFlags`。** getBlocks 只缩小「必须 getBlock 的集合」。

| 格子 | 做法 |
| --- | --- |
| 确认空气 | 不读，flags = 空气 |
| 已导出名单且无状态 | 可用 typeId 缓存的 `evalBlockFlags` 结果 |
| 特殊组（活板门等） | 必须 `getBlock` |
| 非空气但未入任何组 | **必须 `getBlock`**，不得判不可过 |

P8a 验收：同一块地、同一加载范围内，**可站支撑格集合相同，连通分量相同**（场 id 数字允许因遍历序变化）。

### B3. 「找不到可派项」没把「有候选、无就绪」分开

**原则：LSP**（刷新闸门输入契约不完整）

**问题：** 触发节把未命中分成「没有 / 被占 / 场不同 / unready」。漏了农作最常见的一种：兴趣点候选在（麦田、空耕地），查询时无一就绪（没熟、没种子、`plantCooldown`、土地对不上背包种子）。这不是地形过期；按「缓存里找不到可派项」字面，空闲女仆每 60s 会对活动圈 16～25 个区块做 diff——空田痛点只是从「按人慢扫」换成「按圈慢扫」。

**建议：索要结果用判别联合，闸门只吃「表可能过期」的原因。**

```
AskMiss =
  | { reason: "no_candidate" }             → 可刷新
  | { reason: "all_claimed" }              → 不刷新
  | { reason: "none_ready" }               → 不刷新（熟了靠查询时 permutation）
  | { reason: "none_usable" }              → 不刷新（没种子、土地-种子不配、补种冷却）
  | { reason: "all_different_or_unreach" } → 可刷新（最终稿建议再拆，见 M-diff）
  | { reason: "unready" }                  → 不刷新，等建层
  | { reason: "paused" }                   → 不刷新，等 merge/probe
```

`none_ready` / `none_usable` 与 `no_candidate` 必须能区分，不能都叫「未命中」。

### B4. 兴趣点规则写进落脚点扫描，依赖方向会反转

**原则：DIP、OCP、最少知识**

**问题：** 架构节写工作适配层只注册规则、任务板经导出函数问场、不碰 `DimRec`——对的。同文扫描步骤 2 却把作物/土地/甘蔗/瓜/可可写进**建层扫描分组**，步骤 4「写落脚点同时挂兴趣点」。若落在 `StandField` / `ChunkRec` 上：寻路基础设施依赖农作种类；新工作只能改核心扫描；`discardIdle` 丢区块时清兴趣点，把工作缓存生命周期绑死在场模块私有结构上。

**建议：一次扫描、两套消费者，不要一个函数包办。**

```
ChunkSnapshot          ← 只含坐标分组 + 按需 flags（不含 kind）
    ├─ StandField      ← 只消费可站 / 连边
    └─ InterestIndex   ← 只消费已注册规则 + 快照 +「问场」导出函数
```

- `includeTypes` = 谓词导出 ∪ 各规则声明的 typeId（Farm 走 `FarmBlocks`）。
- `ChunkRec` 不出现 `InterestPoint`。
- 兴趣点与区块同生共死，用同一套卸载信号（如 `onChunkDiscard`），兴趣索引自己清，不读 `DimRec`。
- 还要决定谁碰 `chunk.lastUsed`，否则场被丢、兴趣点还挂着。
- **P8a 交付物是快照，不是挂好的五种兴趣点**；禁止 `scanChunk` 里 `if (wheat)`。

### B5. 兴趣点跟着已建层走，但圈内首建没有扫描单元

**原则：LSP**（`collectTasks` 退场后覆盖范围不得缩小）

**问题（Grok 强调为原稿最缺的一块）：** 当前链路两段——`collectTasks` **不依赖**落脚点表，直接按女仆脚下扫方块；`assignNext` 才对起点和候选调用 `ensureStandHeight`。P8 把兴趣点改成「建层时顺手标」后：表里没有的层就没有兴趣点；刷新只对「范围内已建层」做 diff；未建层靠 `ensureStandHeight`，但它只点亮**一点**的三层，不是铺满活动圈。女仆第一次进田、或田在圈内但她还没走过：已建层空 → `no_candidate` → 刷新已建层无操作 → 首建若只在脚下点一次，圈对面的田进不了表。按字面实现，P8b「退场 collectTasks」会把「先扫后建」收成「没建就看不见」——调度覆盖回归，不是性能问题。

**方向（需拍板，不指定唯一）：**

| 方向 | 做法 | 利 | 弊 |
| --- | --- | --- | --- |
| 1 | 未命中时，对活动圈覆盖的每个区块，在工作竖直窗口上 `requestLayers` | 覆盖对齐「圈内可见」 | 最多 25 区块 × 多层；须与 B3、M5、M6 一起做，否则冷启动整圈 `unready` |
| 2 | 已建层查任务板；圈内未建区块单独「轻量兴趣预扫」（只写兴趣点不建落脚点），认领时再 `ensureStandHeight` | 冷启动快 | 两套扫描要防 DRY；未建层同场仍是 `unready` |
| 3 | P8b 仍保留一次圈内 `collectTasks` 作冷启动，只把「重复扫」从热路径拿掉 | 行为最接近现状 | 与「女仆只查缓存」不完全一致，只能当过渡 |

**P8b 验收「同一块田两个女仆只扫一次」之前，必须先写下：圈内未建区域的兴趣点从哪来。**

### B-perf. 稳态 `getBlock` 热点在出发找路，P8a 基准口径错位

**原则：LSP、DRY**（Claude 新增 BLOCKER）

**问题：** 正文把 `getBlock` 开销算在建层上（一区块三层约 2000 次，且是一次性成本）。稳态：`Farm.tryFollowTask` / `CropRoute.assignNext` 每次出发 → `findReversiblePath` → 每展开一叶 `rereadLeaf` → 每叶 `new StandableCache`，每拍上限 256 叶。平地一叶约读 36 个不同格，相邻叶子足迹重叠但缓存每叶一份、**完全不复用**；展开 50～100 叶即 1800～3600 次 `getBlock`（还伴随 `getAllStates`/`getTags`），且每名女仆每次出发付一次。正文把 `StandableCache` 留给「一次性搜索」、只让建层改 getBlocks → P8a 基准（只测建层）大幅下降，游戏里每拍总读量几乎不变。

**建议：**

1. **P8a 前打计数器**，按来源三类统计每拍读量：建层（`scanChunk`）、出发找路（`rereadLeaf`）、工作扫描（`collectTasks`）；测完归档，不常驻 BP。
2. **同拍共享一份 flags 缓存作对照组**：挂 `DimRec`、`resetBudgets` 时清空；`rereadLeaf` 与 `scanChunk` 共用。契约：同拍内 `acquireAt` 改方块后再找路会读到旧值——与「acquire 后局部列刷新」同一钩子处失效。
3. **出发是否仍逐叶重读**列为待拍板；引入 60s diff + 局部刷新后与重读职责重叠，但去掉会改变失效兜底（只能靠 follow fail → `unreachableCache` 30s），不能顺手改。
4. P8a 验收改为：**每拍总方块读取量**（三类之和）下降。

## MAJOR

### M1. `InterestPoint.state` 与「查询时确认就绪」双源

**原则：DRY、LSP**

**问题：** 模型有 `state: "candidate" | "ready"`，同时写就绪在查询时用 `ListBlockVolume` + permutation 筛。`farm_plant` 就绪还依赖**这名女仆**的背包、`plantCooldown`、`Farm.landHasSeed`——不是区块表上的全局状态。把 `ready` 写回共享表会脏；只存 candidate 则 `state` 字段多余，调用方当全局 ready 会错派。

**建议：** 表里只存 candidate（加 `extra`）。就绪是查询视图，按 kind 策略计算，不落盘。`farm_plant` 策略入参是女仆，不是方块。

### M2. TaskBoard 与 `assignNext` 的职责切分；候选池不能先裁成 N

**原则：DRY、DIP、LSP**

**问题：** 正文任务板「套用 cellClaims、活动圈、同场，取最近 N」；现 `Farm.assignNext` 已做完空闲/圈/种子/占用/场认领/不可达缓存/同距收割优先/认领 N/逐格 follow。`CropRoute.assignNext` 还有 `standsBeside` 等，且**没有**队列。更硬的契约：Farm 是**先收最多 25 候选，再按场过滤后取 5**；若任务板只交最近 5 个就绪点，这 5 个全是 unready/different/不可达时，更远可派项看不见。N 是认领上限，不是查询窗口。

**切法（需拍板）：**

| 方向 | 做法 | 利 | 弊 |
| --- | --- | --- | --- |
| A | 任务板 = 缓存查询 + 就绪确认，交出 **>N** 候选池；认领/队列/follow 仍在 Farm、CropRoute | 改动小，P7 硬约束不动 | 圈/同场/占用可能滤两遍，要抽共享谓词 |
| B | 任务板负责到认领 N；工作只留 `acquireAt` + 规则 | 调度入口能收成一次 ask | CropRoute 须先有队列，否则 N>1 占坑不干 |
| C | 任务板产出带 `standKeys` 的候选；工作自己选 stand、认领、follow | 瓜/可可多落脚点仍由工作解释 | 「同场」两边各做一次会漂 |

**最终建议：** P8b 默认试 **A**（Claude 倾向：生命周期入口不动、P7 不动、CropRoute 无队列；B/C 等 P8d 对齐后再议）。另须：占用走端口、不直引各工作 `cellClaims`；按当前工作模式过滤 kind；查询窗口 > N；P8d 前 CropRoute 对齐队列或对该类 N=1。

---

### M3. 名单三处权威；Farm 必须继续认 `FarmBlocks`

**原则：DRY、OCP**

### M5. `layerReady` 会把「正在建的整块」打成不可认领；预算会叠成场暂停
