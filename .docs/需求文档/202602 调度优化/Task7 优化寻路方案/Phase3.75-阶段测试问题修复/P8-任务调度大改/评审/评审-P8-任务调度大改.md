# 评审：P8 任务调度大改

对照稿：`../开发草稿-P8-任务调度大改.md`  
对照实现：`StandField` / `Farm.assignNext` / `CropRoute` / `blockPredicates` / `FarmBlocks`  
维度：DRY / OCP / DIP / LSP / 最少知识（得墨忒耳）。分级：BLOCKER / MAJOR / MINOR。

本文件只写评审与建议，不改方案正文、不落代码。常数（1200 tick、刷新预算、N=5）仍按原稿「待拍板」，此处不另拟合。

---

## 结论

方向正确，可以按分期推进，**但不宜按当前正文直接开工 P8a**。

「可达场 + 共享扫描结果 + 女仆只查缓存」能同时打到三处痛点：多女仆重复扫、空田仍按人节流、落脚点只建不补。三层拆分、刷新方案 A、不订阅方块事件、瓜蒂不查朝向，这些已拍板项建议维持。

正文里有几处**契约互相打架**，若按字面实现，P8a「与旧路径一致」和 P8c「未命中才刷新」会对不上。下面按严重度列出；没有 100% 证据的只给方向，不指定唯一做法。

## 与现状对齐（评审前提）

这些是代码里已经成立、方案必须接住的事实，不是新需求。

| 现状 | 对 P8 的含义 |
| --- | --- |
| `StandNode` 存**支撑格**；`Farm.goalStandOfTask` 是作物格 `y-1` | `InterestPoint.standKeys` 必须是支撑格坐标，不能是脚位或动手格 |
| `scanChunk` 按格 `createLeaf`，合并结果依赖访问顺序 | P8a 验收不能要求「场编号数字相同」，只能要求连通分量相同 |
| `rereadLeaf` / `reversibleSteps` / `expandEdges` 都走 `StandableCache.getFlags` | 扫描快照必须能替换这套读口，不能再并存另一套「按 typeId 猜 flags」 |
| `StandableCache.getFlags` 未加载 → `MISSING`（不当空气） | `getBlocks` 没返回的格**不能**直接当空气 |
| Farm 已有 `getBlocks`（土地 + 成熟 permutation）+ P7 队列；CropRoute 仍是单格、无队列 | TaskBoard 替换的是 `collectTasks`，不是 `assignNext`；CropRoute 在 P7d 之前不能假装已有认领 N |
| `FarmBlocks` 运行时按模组 tester 装作物 / 土地 / permutation | Farm 兴趣名单的权威源是 `FarmBlocks`，不是 `blockPredicates` |
| 可可扫描高度是女仆脚位 `+4`～`-1`；建层只保支撑层 `y-1..y+1` | 兴趣点体积若跟落脚点层绑死，会漏高处可可 |
| `evalBlockFlags` 对未知方块看 `isSolid`：非 solid 默认可过 | 「nonAir 且不在薄片组 → 不可过」会改变未知方块语义，与「名单缺项不影响正确性」矛盾 |
| 调度入口有三处（pulse / search / follow 完成），Farm 与 CropRoute 各写一遍 | SpeedController 退场后，这三处应收敛成一次「向任务板索要」，不要留空转的 `runJob` 扫描 |

## BLOCKER

### B1. 「没出现在 nonAir」当作空气 —— 建层正确性

**原则：LSP**（与现 `StandableCache` 契约不一致）

正文扫描步骤 1：不在 `nonAir` 里的格即空气，直接当净空。  
现实现：未加载 / `getBlock` 失败记 `MISSING`，**不当**可过、不当可支撑。

跨未加载区块时，若 `getBlocks(..., allowUnloadedChunks: true)` 只返回已加载部分（正文自己列为待测），按字面算法会：

- 把未加载格建成假落脚点；或
- diff 刷新时把真落脚点当成「消失」删掉。

风险节写「需实测」，但算法已经把「缺省 = 空气」写成默认。P8a 验收「同一块地落脚点集合相同」在区块边缘会系统性失败。

**建议（先补契约，再写 P8a）：**

1. 扫描结果分三态：空气 / 非空气 / **未知（未加载或 API 未覆盖）**。
2. 未知格：不 `createLeaf`、不 `removeLeaf`、不写兴趣点；与今天 `MISSING` 一样跳过。
3. `allowUnloadedChunks` 的实测放到 **P8a 开工前**，不要放到「之后设计若需要再测」。未测之前刷新范围只能扫已加载区块。

### B2. 「名单缺项只影响性能」与步骤 3 字面算法矛盾

**原则：LSP**（谓词结果必须与 `evalBlockFlags` 可互换）

风险节：子串盖不住的模组方块在第 3 步逐格 `getBlock`，缺名单只慢不快错。  
步骤 3：「脚 / 头格若在 `nonAir` 且不在薄片组 → 不可穿过，无需读。」

这两句不能同时成立。未知非空气若跳过 `getBlock`，就会把「引擎 `isSolid=false`、今天默认可过」的方块判成墙，落脚点集与旧路径不一致。

`evalBlockFlags` 还依赖 `Block.isSolid` / `isLiquid` / `isAir`，不是 typeId 的纯函数。按 typeId 缓存 flags 只对「已证明与状态、与实例无关」的类型合法；活板门正文已排除，但默认分支不行。

**建议：flags 的权威来源仍是 `evalBlockFlags`。** getBlocks 只负责缩小「必须 `getBlock` 的集合」。三态处理：

| 格子 | 做法 |
| --- | --- |
| 确认空气 | 不读，flags = 空气 |
| 已导出名单且无状态 | 可用 typeId 缓存的 `evalBlockFlags` 结果 |
| 特殊组（活板门等） | 必须 `getBlock` |
| 非空气但未入任何组 | **必须 `getBlock`**，不得判不可过 |

P8a 验收应改成：同一块地、同一加载范围内，**可站支撑格集合相同，连通分量相同**（场 id 数字允许因遍历顺序变化）。

### B3. 「找不到可派项」没把「有候选、无就绪」分开

**原则：LSP**（刷新闸门的输入契约不完整）

触发节把未命中分成「没有 / 被占 / 场不同 / unready」。漏了农作里最常见的一种：

- 兴趣点候选在（麦田、空耕地），查询时无一就绪（没熟、没种子、`plantCooldown`）。
- 这不是地形过期，正文自己也说「无需为等作物长熟而重扫」。
- 按「缓存里找不到可派项」字面，空闲女仆每 60s 会对活动圈 16～25 个区块做 diff。空田痛点只是从「按人慢扫」换成「按圈慢扫」，没有消掉。

被占不刷新是对的；但「全是未成熟 / 全是自己种不了的空地」必须与「表是空的」分开。

**建议：索要结果用判别联合，闸门只吃「表可能过期」的原因。** 示例：

```
AskMiss =
  | { reason: "no_candidate" }          → 可刷新
  | { reason: "all_claimed" }           → 不刷新
  | { reason: "none_ready" }            → 不刷新（熟了靠查询时 permutation）
  | { reason: "none_usable" }           → 不刷新（没种子、补种冷却；刷新无益）
  | { reason: "all_different_or_unreach" } → 可刷新
  | { reason: "unready" }               → 不刷新，等建层
  | { reason: "paused" }                → 不刷新，等 merge/probe（正文未写，见 M8）
```

`none_ready` 与 `no_candidate` 必须在任务板里能区分，不能都叫「未命中」。

### B4. 兴趣点规则写进落脚点扫描，依赖方向会反转

**原则：DIP、OCP**

架构节写：工作适配层只注册规则，任务板经导出函数问场，不碰 `DimRec`。这是对的。

同文「使用 getBlocks 优化的扫描」步骤 2 却把作物 / 土地 / 甘蔗 / 瓜 / 瓜蒂 / 可可写进**建层扫描的分组列表**，步骤 4「写落脚点的同时挂兴趣点」。若按此落在 `StandField` / `ChunkRec` 上：

- 寻路基础设施依赖农作种类（DIP）。
- 新工作只能改核心扫描，不能只注册（OCP）。
- `discardIdle` 丢区块时顺带清兴趣点，会把工作缓存的生命周期绑死在场模块私有结构上（最少知识）。

**建议：一次扫描、两套消费者，不要一个函数包办。**

```
ChunkSnapshot          ← 只含坐标分组 + 按需 flags（不含 kind）
    ├─ StandField      ← 只消费可站 / 连边
    └─ InterestIndex   ← 只消费已注册规则 + 快照 +「问场」导出函数
```

- `includeTypes` 的名单 = 谓词导出 ∪ 各规则声明的 typeId（Farm 走 `FarmBlocks`，见 M3）。
- `ChunkRec` 不出现 `InterestPoint`。
- 兴趣点与区块同生共死，用**同一套卸载信号**（例如 `onChunkDiscard(dim, chunkKey)`），兴趣索引自己清，不读 `DimRec`。

分期也要接得住：P8a 只替换建层读方块，扫描结果要能在 P8b 挂上规则，而不是 P8a 把作物写进 `scanChunk`、P8b 再挖出来。

## MAJOR

### M1. `InterestPoint.state` 与「查询时确认就绪」双源

**原则：DRY、LSP**

模型里有 `state: "candidate" | "ready"`，同时写就绪在查询时用 `ListBlockVolume` + permutation 筛。  
`farm_plant` 的就绪还依赖**这名女仆**的背包和 `plantCooldown`，根本不是区块表上的全局状态。

若把 `ready` 写回共享表：作物长熟或换背包会脏。  
若只存 candidate：`state` 字段多余，调用方若当全局 ready 用会错派。

**建议：** 表里只存 candidate（加 `extra`）。就绪是查询视图，按 kind 策略计算，不要落盘。`farm_plant` 的策略入参是女仆，不是方块。

### M2. TaskBoard 与 `assignNext` 的职责切在哪

**原则：DRY、DIP、LSP**

正文：任务板「套用 `cellClaims`、活动圈、同场，取最近 N」；P7 队列语义不变。  
现 `Farm.assignNext` 已经做完：空闲、圈、种子、占用、`classifyFieldClaim`、`unreachableCache`、同距收割优先、认领 N、逐格 `follow`。  
`CropRoute.assignNext` 还多了 `standsBeside` / `standDrop` / `goalBlocksAbove`，且**没有**队列（P7d 未做）。

三种切法，利弊如下（未拍板，不指定唯一）：

| 方向 | 做法 | 利 | 弊 |
| --- | --- | --- | --- |
| A | 任务板 = 缓存查询 + 就绪确认；认领 / 队列 / follow 仍在 Farm、CropRoute | 改动面小，P7 硬约束不动 | 圈 / 同场 / 占用会滤两遍，要抽共享谓词才不违反 DRY |
| B | 任务板负责查询到认领 N；工作只留 `acquireAt` + 规则 | 调度入口能收成一次 `ask` | CropRoute 必须先有队列，否则 N>1 会占坑不干（LSP） |
| C | 任务板产出带 `standKeys` 的候选，工作自己选 stand、认领、follow | 瓜 / 可可多落脚点仍由工作解释 | 「同场」若在两边各做一次，规则会漂 |

**建议至少先拍：**

1. 任务板**不**直接引用 `Farm` / 某个 `CropRoute` 的 `cellClaims`（DIP）。占用用端口：`isFree(dim, pos, maid)` / `claim` / `release`。Farm 与甘蔗占用表本来就不互通，全局一张板会串模式。
2. P8b 只接 Farm 时，认领 N 与「每格必 follow」仍走现有 `assignNext` / `tryFollowTask`，不要在任务板里开近距直收。
3. P8d 删 `collect` 之前，CropRoute 要么补上与 Farm 同契约的队列（原 P7d），要么任务板对该类工作 N=1。不能口头「队列语义不变」却让无队列实现吞 N 个 claim。

### M3. 名单有三处权威，Farm 必须继续认 `FarmBlocks`

**原则：DRY、OCP**

正文要把 `blockPredicates` 的子串提成完整 typeId，供 `includeTypes`。这只覆盖**可站谓词**。  
农作 typeId / 成熟 permutation 的权威已在 `FarmBlocks`（原版 + 农夫乐事 / 玉米乐事 / 餐厨工艺，按 tester 物品动态装）。

若建层扫描再写一份作物 / 土地名单：

- 模组田在兴趣表里消失，但 `acquireAt` / `taskStillValid` 仍认（或相反）；
- 新模组只能改扫描核心。

**建议：**

- 可站：`blockPredicates` 导出「能喂 `includeTypes` 的名单」+「必须 `getBlock` 的特殊组」。
- Farm 兴趣：规则声明 `includeTypes = FarmBlocks.getLands() ∪ 作物 typeId`，就绪 permutation = `getCorpPermutations()`。
- 甘蔗 / 瓜 / 可可：规则自己声明少量原版 id。
- 扫描器只合并「本层已注册规则要的 typeId」，不写死五种 kind。

### M4. 兴趣点高度层与可可 / 高甘蔗对不齐

**原则：LSP**（迁移后工作应覆盖原扫描高度）

落脚点首建：`ensureStandHeight` 只请求支撑 `y-1, y, y+1`，读块大约到脚头附近。  
可可现状：脚位 `+4`～`-1`。瓜 / 甘蔗现状：列上再追若干格。

兴趣点「归属层按 `pos` 的区块与高度」没问题；问题是**候选什么时候进表**。若只在建落脚点层时顺手标：

- 树干上偏高的可可进不了表；
- 刷新「已建层」也补不进来（那一层根本没建）。

「不属于落脚点子集」正文只写了平面邻接，没写竖直范围。

**建议：规则自带「相对本层还要看的 y 偏移」**，快照体积取「可站窗口 ∪ 各规则窗口」的并。P8a 体积可以仍是支撑层窗口；P8d 接可可前必须把并集体积写进验收，不能默认「跟落脚点层相同」。

另：甘蔗落脚点写成「根下方的土」过窄。现状是任意可站支撑 + 上连续 ≥2 `reeds`（沙、草、泥都有）。规则应认落脚点表，不要认「土」typeId。

### M5. 查询时就绪确认可能比建层更撞 `getBlocks` 上限

**原则：最少知识 / 风险与已拍板 5 冲突**

已拍板 5：构建用不上大体积 / `closest`，不预先实测上限。  
查询时却要把活动圈内一批候选做成 `ListBlockVolume` 再 `getBlocks`。家模式 ±32 的麦田，候选可以到上千格，这正是「大体积 / 大返回」路径。

**建议：**

1. 就绪确认按**区块或固定批**切，不要一次塞满圈。
2. 先按距离（及同距收割优先、同距列序）取出 >N 的前缀再确认，避免为圈外远处成熟作物付费。
3. 这一项的上限实测应算 P8b 开工条件，不要沿用已拍板 5。

同一拍多名女仆索要同一圈，确认结果应能共用（DRY），不要每人打一遍 permutation。

### M6. P8c 验收「收瓜后走廊立即走」早于瓜迁移

**原则：LSP**（阶段验收与阶段能力不一致）

局部列刷新写在 P8c，瓜规则在 P8d。P8c 若只给 Farm 的 `acquireAt` 挂钩，瓜仍走 `CropRoute`，走廊问题不会在 P8c 消失。

**方向（二选一，需拍板）：**

1. P8c 验收去掉瓜走廊，只验耕地收后补种改写 + 空田 60s 一刷；走廊放到 P8d。
2. P8c 提供与工作无关的 `refreshColumns(dim, xz列…)`，`CropRoute` 在 `acquireAt` 成功后也调用（得墨忒耳：工作只报「这些列变了」，不碰 `DimRec`）。

方向 2 能更早验证「只建不补」，且不依赖兴趣点 kind。

### M7. 刷新 / 建层 / 合并预算会叠成场暂停

**原则：最少知识、DRY**

一次活动圈 diff：最多约 25 区块 × 已建 3 层。每层都可能 `createLeaf` / `removeLeaf` / `rereadLeaf`，进而 `scheduleMerge` / `startProbe`。  
`busy>0` 时场牌不可认领 → 大片 `paused`。这与否决方案 B「整层重建导致认领全 paused」是同一类症状，只是入口换成 diff。

刷新预算只限制「重扫多少层」，不限制本波产生多少 merge/probe。建层预算仍是每拍 64 个新点；刷新若走同一 `createLeaf` 会和首建抢额度。

**建议：**

- 刷新扫层、首建、merge、probe 四份上限继续分开（现 `budgets.ts` 已是这个模型）。
- 写明：刷新用尽只停刷新；**不要**为了刷完一层而把 merge 额度吃光，导致正在干活的场 `paused`。
- 局部列刷新与圈 diff 走同一套 diff 函数（DRY），但局部列**插队**且体积封顶为「动手格列 + 四邻 × 已建层」。

冷却「按区块」还是「按区块层」正文前后不一致（「每区块 `lastRefreshTick`」vs「冷却从该区块层做完起算」）。建议：键用 `dim + cx + cz + y层`，未做完的层留在刷新队列，已做完的层单独起冷却。

### M8. `paused` 未进入刷新闸门

**原则：LSP**（与现 `FieldClaim` 四值不对齐）

`classifyFieldClaim` 现有 `same | different | unready | paused`。闸门写了前三个，没写 `paused`。  
merge/probe 期间目标场暂停是正常忙碌，再触发圈刷新会叠风暴（见 M7）。

**建议：** `paused` 与 `unready` 一样：不刷新，等预算把牌刷回可认领。

### M9. SpeedController 退场后，三个调度入口没有收口

**原则：DRY、OCP**

退场 `target_lack` 之后，`search` 里 `system.runJob(collectTasks)` 不再有扫描可做。若 pulse、9s search、`onFollowComplete` 仍各写一遍「索要 + 派」，会留下空 `runJob`，新工作还要再抄入口。

**建议：** 工作侧只留一个 `askAndAssign(maid)`（或任务板 `ask` + 现有 `assignNext`）。  
`onSchedulePulse`：卡住兜底 + 空闲则 ask。  
`onFollowComplete`：队列空则 ask。  
`MaidTarget.search`：可删或变成对 `askAndAssign` 的别名，避免第三人再接 `SpeedController`。

缺目标加扫范围（现 `lackmode` 时 `range+10`）随活动圈缓存一起消失。这是行为变化，应写进方案「有意放弃」，不要 silently 消失。

### M10. 连边仍走 `StandableCache` 时，P8a 只换建层读口不够

**原则：DIP、DRY**

正文：`reversibleSteps` 底层取 flags 改为读本次扫描结果。  
现 `reversibleSteps` → `expandEdges(cache)` → `cache.getFlags`；`rereadLeaf` 自己 `new StandableCache`。出发找路仍会 `rereadLeaf`。

若只有 `scanChunk` 改 getBlocks，出发路径仍逐格 `getBlock`，且两套 flags 可能不一致（活板门状态、未知方块）。

**建议：** 先抽「按坐标给 `BlockFlags`」的端口（内存快照实现 + 现 `StandableCache` 实现）。`reversibleSteps` / `rereadLeaf` / 建层只依赖端口。P8a 建层填快照；未覆盖坐标再回退 `getBlock`。不要让 `StandField` 认识 `ListBlockVolume`。

### M11. 跟随圈移动时，「按区块冷却」会漏扫也会重复扫

**原则：最少知识**

跟随：圈心是主人脚，主人走一步，活动圈覆盖的区块集合就变。  
只给圈内区块记 `lastRefreshTick` 是对的；但「未命中 → 刷新圈内冷却外区块」在跟随模式下等于沿路刷新区。这与家模式「一块田 60s 一刷」不是同一负载。

未测，只列方向：

1. 跟随与家用同一闸门，接受走一圈多刷新区（实现简单，可能卡）。
2. 跟随只首建新区、不因「未命中」diff 已建层（漏自然生长，靠局部列刷新）。
3. 冷却键加上圈心所在区块，圈心未跨区块则不新开刷新（折中，需拍板，不是拟合常数）。

P8c 写验收前要选定一种，并写「跟随」用例，不要只写家模式空田。

### m3. 甘蔗「候选即就绪」与「长高靠刷新」

**原则：DRY**

### m4. `standKeys` 跨区块与 `discardIdle`

**原则：最少知识**

兴趣点在 A 块，`standKeys` 指向 B 块。B 被 `discardIdle` 丢掉后，A 上的键变悬空。

丢 B 时不要让兴趣模块去翻 A 的私有表；靠查询时容错即可（与「不监听外界破坏」一致）。
