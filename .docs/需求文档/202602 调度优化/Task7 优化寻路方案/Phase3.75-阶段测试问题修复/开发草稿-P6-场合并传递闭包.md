# P6：同场可认领却不前往（场合并未传递）

## 现象

耕地选点：女仆与作物肉眼同片田，但 `classifyFieldClaim` 长期 `paused` → `different`，`assignNext` 全跳过，不出发。

稳定复现日志：`日志2.log`（修前）/ `日志3.log`（修后）。

## 根因

建点桥接时中间场被**同时**排进两个 merge 目标，写完后两侧仍是不同 `fieldId`，且队列已空：

1. `-61` 桥 `[1,2]` → 排 `2→1`
2. `-67` 桥当时看见 `[2,4]` → 再排 `2→4`
3. 写完：女仆留在 `1`，作物在 `4`；**从未出现 `1↔4`**
4. 两端均 `claimable`、`writes=0` → 永久 `claim_different`

本质：merge 入队按「裸 fieldId」快照，没有传递闭包；队首用入队时的 keys 快照，吃不到上游刚并入的点；写完也不按新邻接补排。

## 方案对比

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A | 仅 `mergeRoot` 归一入队 | 能改 `2→4` 为 `1↔4`；若 keys 仍是入队快照，上游未写入的点可能漏搬 |
| B | 仅写完 `afterMergeRescan` | 能补 `1↔4`；入队期仍可能双挂同一 from，队列噪音大 |
| C（采用） | `mergeRoot` 归一 + merge 队首 `prime` 取现场 nodes + 写完跨场 `afterMergeRescan`；建点邻场按 root 收集 | 入队与落盘都闭合；日志3 已验 |

## 落地（C）

文件：`TouHouLittleMaid_BP/typescripts/src/maid/path/field/StandField.ts`

1. **`WriteJob.kind`**：`merge` | `recolor`（拆场不参与 root 链）。
2. **`mergeRoot`**：沿未完成 merge 的 `release[0]→toId` 传递；`scheduleMerge` 先 root 再 `largerField`，去重。
3. **`prime`**：merge 成为队首时按 from 现场 `nodes` 装填 keys（吃进上游刚写入的点）。
4. **`afterMergeRescan`**：本任务 `doneKeys` 上若仍有跨场可逆边，再 `scheduleMerge`。
5. **`createLeaf`**：邻场 id 经 `mergeRoot` 再桥接（日志3：`-67` 直接 `[1,4]`）。

TEMP 诊断日志已删。

## 验收

1. 同片田选点：合并忙时最多短暂 `paused`；写完后同 `fieldId` 且能 `find path` / `assignNext` 派出。  
2. 桥接不再出现「同一 from 挂两个 to」导致的永久 `claim_different`。  
3. 修后日志特征（日志3）：`touchFields=[1,4]` → `4→1` → `prime keys=…` → 随后连续收种至 `tasks=0`。

## 代码评审（落地后）

审查维度：DRY / OCP / DIP / LSP / 最少知识。分级：BLOCKER / MAJOR / MINOR。

### BLOCKER

无。

### MAJOR

无（日志3 已覆盖原复现路径；下列为契约/可维护性，不阻断合并）。

### MINOR

1. **DRY**：`createLeaf` 先本地 `largerField` 定 `keep`，`scheduleMerge` 内再 root+larger 一次；结果通常一致，属重复决策。可改为只 `scheduleMerge`、叶子直接挂 `mergeRoot` 后的 keep。  
2. **LSP / 契约隐式**：merge 的 from 约定为 `release[0]`（`mergeRoot` / `prime` / `hasMergeJobBetween` 共用）。建议日后给 `WriteJob` 显式 `fromId?: number`，避免与 recolor 的 `release` 语义靠约定区分。  
3. **最少知识**：`afterMergeRescan` 只扫本任务搬动的点；若跨场边只挂在「未搬动」的对端叶子上，依赖对端日后 reread/建点或下一次涉及该边的 merge。当前桥接场景由 `createLeaf`+root 已覆盖；极端拓扑可再考虑双向扫或 plaque 邻接索引。  
4. **OCP**：`kind` 区分 merge/recolor 合理；若再增多写任务类型，宜收成小策略而不是继续堆 `if (kind === …)`。

### 结论

**通过。** 根因与修复对齐，复测日志符合预期；MINOR 不强制本轮改，可记技术债。
