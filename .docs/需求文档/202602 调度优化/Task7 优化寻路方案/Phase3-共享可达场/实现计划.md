# Phase3：共享 Standable 与 ROI 可达场（方案 D + C）

**目的：** 农作大范围监测下，让多女仆复用方块谓词与「站立格→作物」可达查询，降低反复 A\* / `getBlock` 成本，并支撑更大搜寻半径。  
**状态：** 设计已定（只做 **D、C**）；**未开工**。  
**相关：** [总实现计划](../实现计划.md) Phase 3 农作接线；现有 `StandableCache` / `edges` / `AStar` / `Path.canReach`。

**明确不做：**

| 弃案 | 原因 |
| --- | --- |
| **A** 共享不可达负表 | C 建成后，不在可达集即不可认领；Fail 以脏 ROI 重建为主，负表可有可无 |
| **B** 起点量化正缓存 `(startQ, goal)→ok` | 对指定 goal 的逆向可达集查询已覆盖其效用 |

现有 `UnreachableCache`（per-maid Fail ban）可保留作过渡，**不纳入本 Phase 核心交付**。

---

## 0. 结论（最简可行）

```
ROI（农田区域）:
  D: 共享 StandableCache（warm 一次，同 ROI / 短窗内复用）
  C: 以作物站立格为多种子源，按与 A* 相同的边规则做逆向 BFS/Dijkstra
      → 每 goal（或 goal 批次）得到「能到达该 goal 的站立格集合」或距离场

认领前:
  maidStand ∈ reachable(goal)  ?  可认领并 Path.follow
              :  跳过（不必再跑全量 canReach A*；可选抽检）

地形变化 / follow Fail:
  标记 ROI dirty → 下次访问重建 D+C（TTL 保底）
```

---

## 1. 方案 D — 共享 `StandableCache`

### 1.1 问题

每次 `Path.find` / `canReach` 都 `new StandableCache` + `warmBox`，农作多女仆、多候选时重复扫同一片田。

### 1.2 目标

- 同一 **dimension + ROI 包围盒**（或同 tick / 短 TTL）内，**一份**方块 flags 供边展开与可达场共用。
- 谓词仍唯一来自 `blockPredicates.ts`，不另开公式。

### 1.3 建议形态

| 项 | 建议 |
| --- | --- |
| 模块 | `path/SharedStandable.ts` 或扩展 `StandableCache` 增加进程内租约 |
| 键 | `dimId + min+max`（或 chunk 集合哈希） |
| 生命周期 | 引用计数 / 短 TTL（如 1～5s）/ ROI 脏时丢弃 |
| API | `acquire(dim, bounds) → StandableCache`；`release` 或自动过期 |
| 与单次 find | `Path.runFind` 优先向共享层借缓存；无则自建（行为与今一致） |

### 1.4 验收

- 同 ROI 连续两次 `warm` 不重复扫方块（可用计数/日志探针）。
- 脏标记后下次必定重新 `warm`。
- 单女仆 `path_go` 行为与改前无回归。

## 2. 方案 C — ROI 多源逆向可达场

### 2.1 问题

可达依赖起点；不能做「与起点无关」的全局布尔表。农作需要的是：  
**「当前站立格能否到达这个作物脚位」**，且多女仆共享查询。

### 2.2 语义（必须）

对 ROI 内每个（或每批）目标支撑格 `goal`：

- 在已 warm 的 `StandableCache` 上，用与 `expandEdges` **相同**的边（Walk / Jump1 / Fall / SprintGap），做 **从 goal 出发的逆向** BFS/Dijkstra（边反向：若 `u→v` 存在则逆向扩 `v→u`）。
- 得到集合 `R(goal) = { stand | stand 能到达 goal }`（或距离场 `dist(stand, goal)`）。
- 查询：`canReachCached(maidStand, goal) := maidStand ∈ R(goal)`（O(1) / O(log)）。

**注意：** 「能到田里任意作物」的并集 `⋃ R(g)` **不能**单独替代对**指定**作物的认领判断；认领必须查 `R(该 goal)`。

### 2.3 ROI 怎么划（实现时二选一，首版建议①）

| # | 划法 | 说明 |
| --- | --- | --- |
| ① | 以扫描中心（女仆/小队锚点）为中心的箱 | 与现 `SEARCH_H/V` 对齐，易接 `Farm.search` |
| ② | 按 chunk / 固定农田区块 | 大田更稳，需 chunk 脏与多 ROI |

首版常量可仍用 `SEARCH_H=16`、`SEARCH_V=4`，共享后再评估放大（如 24/±6）。

### 2.4 建议形态

| 项 | 建议 |
| --- | --- |
| 模块 | `path/ReachabilityField.ts`（或 `FarmReachIndex.ts`） |
| 持有 | `StandableCache` 引用 + `Map<goalKey, Set<standKey> \| Float32距离>` |
| 种子 | ROI 内已知 `thlmt:farm` 目标脚位 / 扫描得到的候选支撑格 |
| 预算 | `maxExpand` / `maxMs`（可高于单次 A*，但要可分帧） |
| 对外 API | `ensureField(roi)`；`isReachable(stand, goal)`；`invalidate(roi)` |
| 与 Path | `Path.canReach` 在 ROI 命中时走字段；未命中或 ignoreCache 时回退 A* |

### 2.5 失效

| 触发 | 动作 |
| --- | --- |
| TTL（如 5～15s） | 到期作废，下次访问重建 |
| 方块变化（若有监听）/ 显式 `invalidate` | 脏 ROI |
| `Path.follow` Fail 到某 goal | 至少脏该 goal 的 `R(g)`，或整 ROI |
| 作物标记 despawn / 新 place | 增删种子；增量重建或脏 ROI |

**不做：** 持久化到磁盘。

### 2.6 验收

- 平地连通：女仆站立格 ∈ `R(goal)` 与 `Path.find(...).ok` 一致（抽检 ≥N 点）。
- 隔沟需 Gap：有 SprintGap 边时字段与 A* 一致；无边时均不可达。
- 两女仆同 ROI：只建一场，两次查询无第二次全量逆向（日志计数）。
- Fail 后脏：原假阳性路径不再被认领（或重建后纠正）。

## 3. 与 Phase3 农作接线的关系

| 步骤 | 依赖 |
| --- | --- |
| `Farm.search` / `place*` 扩范围 | D 降低扫块成本；C 非必须但利于后续过滤 |
| 认领前过滤 | **C**：`isReachable(maidStand, cropStand)`；通过后再 `Seek` + `Path.follow` |
| 双女仆不抢 | 仍靠 Seek stamp；C 只解决「谁能走到」，不解决所有权 |

建议实现顺序：

1. **D** 共享 Standable（可单独合入，立减 warm 重复）  
2. **C** 可达场 + `canReach` 挂钩  
3. Farm 认领改走 C（总计划 Phase 3 勾选）

## 6. 风险

| 风险 | 缓解 |
| --- | --- |
| 逆向边漏/多重导致与 A* 不一致 | 共用同一 `expandEdges`；抽检差分测试 |
| ROI 过大单次建场卡顿 | 预算上限 + 分帧；首版箱体勿盲目加大 |
| 只建并集导致错认领 | API 强制按 **指定 goal** 查询 |
| 脏不及时假阳性 | Fail 必脏；TTL 保底 |
| 与现 `UnreachableCache` 双轨困惑 | 文档标明 C 为主；负表不扩展 |
