# 寻路基建

先把需要反复寻路的工作共用的那套结构定下来，再把农作等模式接上去。

## 寻路原则

- 农作这类工作会不停找下一格，而且**一个目标只能由一个女仆认领**。方块信息和「哪些落脚点互相走得到」要共用，避免每个女仆反复读同一片地。
- 持续工作只用**来回都走得通**的步。女仆从 A 去 B，从 B 也要能回到 A，否则不去 B。平地互走、跳上一格再落下一格，算来回都通。落下两格及以上跳不回去，不进这套共享数据。
- 一次性寻路不进共享数据，用完即弃，允许落下多格。跨沟属于可逆步，进共享数据。

真正卡住女仆的不是寻路步数，而是她被允许活动的那一圈：

- 家模式以家的坐标为中心。女仆和 NPC 以外的状态，回家范围是水平各 32 格的方框，出框或换了维度会被传送回家中心。NPC 的这个方框只有 2 格。
- 跟随主人时，以主人位置为中心，超出距离同样不应把圈外的点当成目标。

圈外的落脚点可以留在共享数据里（别的女仆、别的家用得上），但**这个女仆不能认领圈外的点**。脚本寻路进行时不执行回家传送，所以圈外的格子可以作为途经格。这一圈只限制目标，不限制路怎么绕。

认领仍只选圈内目标。同一片可逆区域里，步数可以放得很宽，甚至不设上限。搜索范围是整片场，不再用这一圈把路截断。

## 落脚点表

所有工作模式共用一张表，按 **维度 → 区块 → 落脚点** 存放。区块内用一张坐标表直接找到落脚点，不按高度分层，也不按竖列分组。

要查的是某一个坐标、它旁边几格，以及方块改动时同一竖线上大约三个高度。这些都是点查。平走的邻居虽在同一高度，仍然是查旁边那几格，不必扫整层。一块耕地往往有上百个落脚点且几乎同一高度。按竖列会为每个落脚点各做一张只有一项的表，对象开销大一个数量级。

以后若「按高度列出这一区块的全部落脚点」真成了热路径，再加一张高度索引。主键不要改成竖列。

每个落脚点记三样：

- 这一格现在还能不能站。
- 可逆邻居，并且**带走法**：平走、跳上一格、落下一格、跨沟。只存坐标不够，出发时会用另一套规则重推走法，和这张表不是同一张图。
- 所属的场编号。

不在落脚点上记整条路，也不记「到每个目标的下一跳」。一片田上千个落脚点、再乘上多个目标，完整路径会到几十兆，挖掉一格还要整片作废。绕到区域中心再走去目标的树很省，但隔壁一格会绕整片田，农作不能用。

可以另留一份很小的缓存：只记住刚刚真正出发过的那几条路，地形变了整份扔掉。它不参与认领，只避免同一对起终点连算两次。

## 可达场

场是落脚点用可逆步连成的一片。同一场里任意两点都能经过若干次可逆步互相走到。场在所有工作模式之间共用，世界上可以同时有多片。

可逆步只包括：

- 双向平走。
- 成对的跳上一格和落下一格（低的那一侧头顶要空，才能跳回去）。
- 跨沟。空沟两端都能落，来回就是同一条沟，与双向平走相同，不再额外要求「扫描时两侧谁先被选中」。有一格高差时，与跳上、落下相同，只要求低的一侧头顶能跳回去。

现在每个方向只留最近一跳、且先试平跳再试低一格，可能扫出单行边。那是生成顺序的问题，建场时按沟的两端成对写入，不要因此把跨沟排除。落下两格及以上跳不回去，不进场。

两个落脚点之间新出现一条可逆步，且场编号不同，就合并成一场。合并在加边时顺手做，不必全局两两扫描。

挖掉中间一格时场可能裂开。只改被挖的那一格不够。从它原来的邻居重新染色：还能互相走到就仍是一场，走不到就拆成新的场编号。并查集只能合并、不能拆开，不能当作最终做法。跨沟半径内的邻居也要重算：踏脚消失后，旁边可能多出一条新的可逆步，场未必裂开。

同一场就说明两点之间有可逆的路，可以把圈内、没被占用的点认领为目标。认领不需要先把那条具体的路逐格找出来。

具体走法在出发时沿着可逆邻居找。找的时候用叶子上的邻居，目标在圈内，途经格可以在圈外。找路的结果：

| 结果 | 含义 | 怎么处理 |
| --- | --- | --- |
| 拿到路 | 每一步都是当前这场里的可逆步；目标在圈内，途经格可以在圈外 | 可以出发 |
| 证明走不到 | 这一代落脚点里确实没有路能到这个目标 | 才允许拆边、拆场 |
| 不知道 | 区块还没加载好，或这一拍预算用尽 | 这一拍跳过。只给这个女仆记一次短的「未知」，不改场 |

目标被活动圈限制，路可以绕出这一圈。正常情况下同一场里的现算应当能算完。「不知道」留给区块未就绪和偶发的单拍预算，不作为日常拒绝目标的手段。脚本寻路期间不执行回家传送，避免人在圈外的途经格上被拉回家。

追逐超时、互相堵住、路点名额用完，是走路失败，只禁止这个女仆短时间内再试这个目标，不改场编号。不要把堵车写成「这格走不到」。

出发前，场编号和现算必须都同意。出发之后这一段路归这次行走。前方落脚点若失效，取消这次行走（不记成不可达），再按她脚下此刻的落脚点重新认领。人在沟里、水里、空中时，脚下没有落脚点，不要沿用上一个场编号。

## 目标点

目标由工作模式自己维护：要去哪一格、谁占着。它不是落脚点的属性。作物格要先换成脚下那块可站的土，再问这张表。

认领顺序：

1. 目标在活动圈内，且没被别的女仆占着。
2. 女仆脚下的落脚点和目标落脚点场编号相同。同一场即有路。

出发时再沿着可逆邻居找出具体走法。目标在圈内，途经格可以在圈外。

脚下落脚点的算法只能有一个。锚点、脚位反推、作物下方一格必须得到同一个坐标，否则场门和现算对的不是同一格。

## 维护

方块被挖或被放时，只把所在区块标脏。下次有人查这个区块里的落脚点，再重算这一区块，并更新受影响的场。不要定时把所有落脚点重读一遍。

区块从这张表拿掉，按整块进行。脚本侧不一定有「区块卸载」事件，不能依赖它。周围没有玩家、也没有正在干活的女仆，静置一段时间后丢掉整块上的落脚点和边，相关的场按上面的办法拆开或作废。

水算不算危险会改变能不能站。表里保存的应是方块事实（能不能当地面、能不能穿过、是不是危险），「算不算落脚点」按工作规则推导。否则不同工作无法共用一张表。

拆场要在一次认领看得见的范围内做完，不能把半新半旧的场编号露给正在选目标的女仆。

## 和一次性寻路的边界

落下两格以上只允许即用即弃的那次寻路使用。那次寻路不读、不写落脚点表和场编号。跨沟进场。

工作模式默认不走这一条。若以后允许用一次性寻路跳进低一层的田，落地的那一格在成为可逆落脚点之前，不得并进工作用的场。

## 附录：和现有代码的对照

只在改代码时用。

| 文档里的说法 | 现在的代码 |
| --- | --- |
| 落脚点、能不能站 | `StandableCache` / `SharedStandable` |
| 现有的「哪些站立点到得了某个目标」 | `ReachabilityField`，按目标存集合，不存路，大约 10 秒过期 |
| 全边寻路（含落下多格、跨沟） | `AStar` + `expandEdges`，展开大约 2000 步或 50 毫秒 |
| 出发后怎么走 | `Executor`：平走会抽稀，跳上和落下交给追逐，跨沟用冲量 |
| 走路失败后短时间不再试 | `UnreachableCache`，按维度、女仆、终点，大约 30 秒 |
| 回家传送 | 家坐标水平各 32 格的方框（NPC 为 2 格），出框或换维度传送回家中心。脚本寻路期间不执行 |
